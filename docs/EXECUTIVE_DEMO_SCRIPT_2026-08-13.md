# Price Analyzer 임원 발표·시연 대본

기준일: 2026-08-13  
권장 발표 시간: 12~15분, 질의응답 10분  
권장 시연 순서: `정제 검토 → 표준 DB → 신규 견적 분석`

## 1. 발표에서 끝까지 유지할 핵심 메시지

> Price Analyzer는 가격을 임의로 예측하는 시스템이 아니라, 회사가 실제로 받은 과거 견적과 확인 가능한 외부 가격을 근거로 신규 견적의 검토 우선순위와 협상 목표를 제시하는 구매 의사결정 지원 도구입니다.

발표 내내 다음 세 가지를 반복한다.

1. **회사 내부 근거를 먼저 사용한다.**
2. **근거가 부족하면 값을 만들지 않고 판정 대기로 남긴다.**
3. **모든 숫자에서 원본 견적서까지 돌아갈 수 있다.**

피해야 할 표현:

- “AI가 정답 가격을 맞힙니다.”
- “모든 견적을 자동 승인할 수 있습니다.”
- “절감 예상액은 실제 확정 절감액입니다.”
- “현재 데이터가 100% 정제됐습니다.”
- “시장가 사이트에서 모든 설비 가격을 찾을 수 있습니다.”

대신 다음처럼 말한다.

- “반복 검토를 자동화하고 사람이 확인할 대상을 좁힙니다.”
- “근거가 충분한 항목만 자동 판정합니다.”
- “절감 가능성을 보여주는 협상 기준입니다.”
- “미확인 데이터는 숨기지 않고 별도 대기열로 관리합니다.”

## 2. 전체 발표 흐름

| 구간 | 시간 | 화면 | 한 문장 결론 |
|---|---:|---|---|
| 도입 | 1분 | 발표자료 또는 첫 화면 | 수작업 견적 검토를 근거 중심의 반복 가능한 절차로 바꿨다. |
| 개발 과정 | 1분 | 발표자료 | 원본 수집, 정제, 표준 DB, 신규 분석 순서로 단계적으로 구축했다. |
| 정제 검토 | 3분 | `/cleansing` | 자동화가 애매한 항목은 원본과 함께 사람에게 돌려보낸다. |
| 표준 DB | 3분 | `/standard-prices` | 과거 견적을 품명·사양·단위별로 묶고 가격 범위와 원본을 보존한다. |
| 신규 견적 분석 | 5분 | `/analysis` | 적정성 판정과 구매 협상 목표를 한 번의 업로드로 확인한다. |
| 한계·운영안 | 2분 | 결과 화면 | 100% 예측보다 근거 없는 자동판정을 막는 것을 우선했다. |
| 결론 | 30초 | 분석 요약 | 구매 담당자의 시간을 줄이고 협상 근거를 조직 자산으로 축적한다. |

## 3. 도입 대본

### 3.1 문제 제기

“지금까지 견적 검토는 담당자가 과거 파일을 직접 찾고, 비슷한 품목을 눈으로 비교하고, 필요하면 외부 사이트까지 다시 검색하는 방식이었습니다. 이 방식은 담당자의 경험에는 의존하지만, 왜 적정하다고 판단했는지 조직 차원의 근거를 다시 확인하기 어렵습니다.”

“이번 프로젝트의 목적은 구매 담당자를 없애는 것이 아닙니다. 사람이 반복해서 하던 검색과 계산을 줄이고, 중요한 예외와 협상 대상에 집중하게 만드는 것입니다.”

### 3.2 해결 방식

“과거 견적 원본을 읽어 품목별 가격 근거를 만들고, 신규 견적을 올리면 먼저 내부 표준 DB와 비교합니다. 내부 근거가 없을 때만 DeviceMart와 Mouser 시장가를 확인합니다. 그래도 근거가 없으면 가격을 추측하지 않고 판정 대기로 남깁니다.”

### 3.3 개발 과정

“개발은 네 단계로 진행했습니다. 첫째, 제각각인 엑셀·PDF 견적을 읽었습니다. 둘째, 수량·단가·금액 오류와 중복 복사본을 분리했습니다. 셋째, 정제된 과거 견적만으로 표준 DB를 만들었습니다. 넷째, 신규 견적의 가격 적정성과 구매 목표가를 각각 다른 목적의 화면으로 구현했습니다.”

“가격 계산은 설명 가능한 규칙과 통계로 고정했습니다. 사내 AI는 표현이 다른 유사 품목 후보를 찾는 보조 수단이며, 가격을 임의 생성하지 않습니다.”

## 4. 1페이지 — 정제 검토

### 4.1 화면 진입

**화면 조작**

1. 상단 `정제 검토`를 누른다.
2. 왼쪽 검토 대기 건수와 사유 필터를 가리킨다.
3. 기본으로 선택된 `단가 편차 큼` 항목의 오른쪽 상세를 보여준다.
4. 단가 분포의 현재 가격, 중앙값, 차이율을 차례로 가리킨다.
5. 유사 품목의 `원본 보기`와 하단 원본 셀 미리보기를 보여준다.
6. `포함`과 `제외` 버튼은 누르지 않고 의미만 설명한다.

**대본**

“첫 화면은 자동 분석이 확신하지 못한 항목만 모아둔 검토 대기열입니다. 현재 화면의 1,039건은 오류 1,039건이라는 뜻이 아닙니다. 자동으로 포함하기에는 추가 확인이 필요한 항목을 모아둔 것입니다.”

“예를 들어 이 품목은 현재 단가가 630만 원이고, 동일한 품명·사양·단위로 묶인 과거 6건의 중앙값은 800만 원입니다. 차이는 마이너스 21.2%입니다. 시스템은 단순히 ‘이상하다’고만 말하지 않고, 비교에 사용한 6개 가격과 각 원본 파일을 함께 보여줍니다.”

“아래에는 실제 견적서의 머리글과 대상 행을 같이 표시합니다. 담당자는 원본까지 확인한 뒤 포함 또는 제외를 결정하고 판단 근거를 기록합니다. 이 결정은 기존 데이터를 덮어쓰지 않고 새 이력으로 남습니다.”

### 4.2 검토 사유 드롭다운 설명

| 드롭다운 | 발표 설명 | 임원이 물을 수 있는 질문 | 권장 답변 |
|---|---|---|---|
| 모든 사유 | 현재 사람이 확인해야 할 전체 대기열 | 왜 이렇게 많습니까? | 다양한 원본 양식과 OCR 항목을 억지로 자동 포함하지 않았기 때문입니다. 대기 건수는 숨겨진 오류가 아니라 관리해야 할 업무량입니다. |
| 금액 불일치 | 원본의 계산 요소로 산출한 금액과 표시 금액이 다른 행 | 수량×단가만 계산합니까? | 아닙니다. 원본에 일수·인원·수량 같은 요소가 있으면 함께 계산하며, 복합 합계 행은 단순 불일치로 처리하지 않습니다. |

| 수량 확인 필요 | 수량의 의미나 숫자를 확정하지 못한 행 | 수량 0도 오류입니까? | 수량 0·금액 0·유효 단가 조합은 정상으로 인정합니다. 수량 0인데 금액이 존재하는 등 의미가 충돌할 때만 검토합니다. |

### 4.3 정제 화면 예상 꼬리질문

**Q. 이 판단을 사람이 매번 해야 하면 자동화의 의미가 없지 않습니까?**  
“모든 행을 보는 방식에서 예외만 보는 방식으로 바꾸는 것이 1차 효과입니다. 검토 이력이 쌓이면 같은 양식과 같은 사유의 자동처리 범위를 안전하게 넓힐 수 있습니다.”

**Q. 포함을 잘못 눌렀으면 어떻게 합니까?**  
“기존 판단을 삭제하지 않고 새 판단을 추가합니다. 언제 누가 무엇을 근거로 바꿨는지 남기므로 되돌림과 감사가 가능합니다.”

**Q. 단가 편차 기준은 무엇입니까?**  
“같은 그룹 안에서 중앙값과 MAD라는 이상치 기준을 사용합니다. 다만 통계가 최종 업무 판단을 대신하지 않으며, 비교 원본을 화면에서 반드시 함께 제공합니다.”

**Q. 왜 품명·사양·단위로 묶습니까?**  
“현재 원본에서 공통으로 확보 가능한 최소 식별 정보이기 때문입니다. 제조사 모델번호가 확인되면 함께 사용하지만, 없는 값을 추정해 강제로 합치지는 않습니다.”

## 5. 2페이지 — 표준 DB

### 5.1 화면 진입

**시연 전 주의**

- 이 화면은 첫 조회가 수 초 걸릴 수 있으므로 발표 전에 한 번 열어 둔다.
- `최근 갱신`에 성공 빌드 시각이 표시되고 목록이 보이는지 확인한다.
- 발표 직전 `구축 기록 없음` 또는 계속 `불러오는 중`이면 시연을 시작하지 말고 백엔드와 DB 상태를 먼저 확인한다.

**화면 조작**

1. `표준 DB`를 누른다.
2. `데이터 구축 현황`을 펼쳤다가 다시 접는다.
3. 검색창에 발표용 품목을 검색한다.
4. `근거` 드롭다운을 `근거 2건 이상`으로 변경한다.
5. 품목 한 건을 선택해 최저·중앙값·평균·최고를 보여준다.
6. 견적 제출사, 제품 제조사, 견적일 범위를 보여준다.
7. 가격 근거의 `원본 견적서 열기`를 가리킨다.
8. 업데이트 로그를 보여준다.

**대본**

“표준 DB는 외부 판매가격 모음이 아닙니다. 회사가 실제로 받은 과거 견적 중 정제가 끝난 항목을 품명·사양·단위별로 묶은 내부 가격 기준입니다.”

“최신 정상 빌드 기준 표준 품목은 7,092개이고, 가격 통계에 실제로 반영되는 대표 관측은 15,630건입니다. 같은 파일의 복사본은 가격 건수를 부풀리지 않도록 한 건만 계산하고, 복사본의 이력은 감사용으로 연결해 보존합니다.”

“품목을 선택하면 최저·중앙값·평균·최고가 나옵니다. 신규 견적의 중립적인 적정성 판단에는 중앙값을 사용하고, 최저값은 협상 목표를 만들 때 별도의 엄격한 조건으로 사용합니다.”

“견적 제출사와 제품 제조사는 다른 정보입니다. 견적 제출사는 우리에게 견적을 낸 업체이고, 제품 제조사는 해당 부품을 만든 브랜드입니다. 원본에서 확인하지 못한 값은 임의로 채우지 않습니다.”

### 5.2 데이터 구축 현황 접이식 영역

**대본**

“이 영역은 현재 데이터의 한계를 숨기지 않기 위한 품질 현황입니다. 현재 감사 대상 706개 중 483개에서 품목을 추출했고, 223개는 추가 파서·OCR·보안해제본 재수집·미지원 형식 확인이 필요합니다.”

“품목을 추출한 파일이 모두 표준가격이 되는 것도 아닙니다. 현재 226개 파일만 실제 표준가격 근거에 기여합니다. 나머지는 중복, 정제 대기, 가격 필드 부족, 합계 행 등의 이유로 자동 가격 근거에서 제외될 수 있습니다.”

### 5.4 표준 DB 예상 꼬리질문

**Q. 표준단가는 회사가 실제로 지급한 가격입니까?**  
“현재는 회사가 받은 과거 견적 가격입니다. 최종 발주·검수·지급 가격과 동일하다고 보장할 수 없습니다. 운영 고도화 단계에서 구매발주서와 실제 지급 데이터를 연결하면 가장 큰 품질 개선이 가능합니다.”

**Q. 7,092개면 왜 모든 신규 품목이 매칭되지 않습니까?**  
“같은 이름이라도 규격·단위·모델이 다르면 다른 품목입니다. 반대로 이름이 달라도 같은 물건일 수 있습니다. 잘못 합치는 위험이 더 크기 때문에 확실한 경우만 자동 매칭합니다.”

**Q. 평균 대신 왜 중앙값을 사용합니까?**  
“견적 데이터에는 한두 건의 매우 큰 값이 섞일 수 있습니다. 중앙값은 이런 극단값의 영향을 덜 받아 중립적인 비교 기준에 적합합니다.”

**Q. 최저·최고가 같고 근거가 여러 건이면 중복 아닙니까?**  
“가격이 같다는 이유만으로 중복은 아닙니다. 서로 다른 시점이나 다른 업체가 같은 가격을 제시할 수 있습니다. 동일 복사본은 원본 계보와 값으로 대표 한 건만 계산합니다.”

**Q. 업데이트 로그는 무엇입니까?**  
“정제 결정이나 원본이 추가되어 표준가격이 다시 계산된 이력입니다. 기존 버전을 지우지 않기 때문에 과거 분석 당시 어떤 가격을 썼는지 재현할 수 있습니다.”

**Q. ‘원본에서 확인되지 않음’이 많은 이유는 무엇입니까?**  
“원본에 제조사·제출사·날짜가 없거나 위치가 일정하지 않기 때문입니다. 잘못된 업체명이나 임시 날짜를 채우는 것보다 미확인으로 남기는 것이 안전합니다.”

**Q. 엑셀 다운로드는 왜 있습니까?**  
“업무의 핵심은 웹 분석이지만, 회의자료나 오프라인 검토가 필요한 경우 현재 필터 결과를 전달하기 위한 보조 기능입니다.”

### 6.6 구매 목표가 예상 꼬리질문

**Q. 왜 평균이나 중앙값이 아니라 최저값입니까?**  
“임원 관점의 협상 목표는 가장 유리했던 실제 사례를 출발점으로 삼는 것이 적합하다는 정책 결정입니다. 다만 현실적인 적정성 판단은 별도 탭에서 중앙값으로 확인합니다.”

**Q. 최저값이면 비정상 저가를 목표로 잡을 수 있지 않습니까?**  
“정제에서 포함된 가격이고 원본 날짜가 직접 확인된 관측만 사용합니다. 그래도 수량·계약조건 차이는 남을 수 있으므로 최종 구매가가 아니라 협상 출발점으로 표현합니다.”

**Q. 왜 소비자물가 총지수입니까?**  
“공식적이고 장기간 일관된 단일 기준으로 과거 화폐가치를 보정하기 위해 선택했습니다. 다만 설비별 원가를 정확히 설명하는 지수는 아니므로 향후 품목군별 생산자물가·환율·원자재 지수를 병행하는 것이 고도화 과제입니다.”

**Q. 물가 자료가 중간에 하나 빠지면 어떻게 합니까?**  
“다른 지수로 임의 대체하지 않고 목표가 산정에서 제외합니다. 계산 연속성이 확인돼야만 목표가를 보여줍니다.”

**Q. 목표가 대비 차액이 곧 절감액입니까?**  
“아닙니다. 협상 가능한 잠재 차액입니다. 실제 절감액은 최종 발주 가격과 계약조건이 확정된 뒤 측정해야 합니다.”

**Q. 목표 단가 합계는 무슨 의미입니까?**  
“품목별 개당 목표 단가를 단순 합산한 참고값입니다. 재무적으로 중요한 값은 수량을 반영한 목표 금액 합계입니다.”

## 7. 왜 현재 시스템에서 100% 정합한 값이 나올 수 없는가

### 7.1 임원에게 먼저 말할 짧은 답변

> 견적 데이터는 동일한 회계 전표처럼 형식이 고정된 데이터가 아닙니다. 파일 양식, 품명, 단위, 사양, 계약조건이 제각각이고 원본 자체에 빠진 정보도 있습니다. 따라서 100% 자동 정답을 주장하는 대신, 확실한 값만 자동 사용하고 애매한 값은 근거와 함께 사람에게 돌려보내도록 설계했습니다.

### 7.2 정합성의 네 단계

| 단계 | 100%가 어려운 이유 | 현재 방어 장치 |
|---|---|---|
| 파일을 읽는 정확성 | 병합 셀, 수식, 다중 머리글, 구형 XLS, 보안 파일, 스캔 PDF, 깨진 글꼴 | 원본 위치 표시, 파서 버전 관리, OCR 고신뢰 조건, 재수집 상태 분리 |
| 동일 품목 판별 | 같은 제품의 표기가 다르고, 같은 이름이 다른 사양을 의미할 수 있음 | 품명·사양·단위·모델을 보수적으로 비교하고 모호하면 판정 대기 |
| 가격 비교 가능성 | 수량, MOQ, 세금, 운송, 설치, 환율, 납기, 보증, 개정 사양이 다름 | 원본 근거와 가격 범위 표시, 외부 가격 조건 확인, 강제 병합 금지 |
| 미래 협상가 추정 | 물가 총지수가 특정 설비의 원가·기술 변화·공급 부족을 모두 설명하지 못함 | 목표가는 예측값이 아닌 협상 앵커로 제한하고 적정성 판단과 분리 |

### 7.3 현재 데이터로 확인되는 구체적 한계

- 현재 감사 대상 706개 중 품목 추출 완료는 483개다. 약 68.4%의 파일에서 품목을 추출했으며, 223개는 추가 처리가 필요하다.
- 추가 처리 대상에는 추가 파서 107개, OCR 56개, 열기 실패·재수집 57개, 보안해제·정상본 필요 53개, 미지원 형식 3개가 포함된다. 항목 간 일부는 상태 정의상 겹치거나 복구본으로 상쇄될 수 있으므로 단순 합계로 전체를 계산하지 않는다.
- 현재 검토 대기 1,039건은 남아 있는 불확실성이다. 자동 포함률을 높이기 위해 이 수치를 숨기거나 강제 처리하면 오히려 표준 DB가 오염된다.
- 과거 견적은 최종 지급가격이 아니라 제출가격일 수 있다.
- 견적 제출사, 제품 제조사, 견적일이 원본에 명시되지 않은 경우가 있다.
- DeviceMart·Mouser는 공개 유통 부품에는 유효하지만 주문제작 설비·가공·설치 인건비에는 가격이 없는 경우가 많다.
- 사내 의미 검색은 유사 후보를 찾는 데 도움을 주지만, 두 품목의 동일성을 자동으로 보증하지 않는다.

### 7.4 “정확도가 몇 퍼센트냐”에 대한 답변

“현재는 하나의 정확도 숫자로 말하면 오해가 생깁니다. 파일 추출률, 품목 매칭률, 가격 판정 커버리지, 담당자 최종 일치율을 분리해 측정해야 합니다.”

“현재 확인 가능한 파일 추출률은 483/706, 약 68.4%입니다. 시연 견적의 30/32 매칭률은 기능 확인을 위해 구성한 샘플 결과이지 전체 업무 정확도가 아닙니다. 실제 정확도는 대표 실무 견적 표본을 구매 담당자가 판정한 결과와 대조하는 파일럿으로 산출해야 합니다.”

권장 파일럿 KPI:

1. 파일·품목 추출 성공률
2. 표준 DB 자동 매칭률
3. 가격 판정 가능 금액 커버리지
4. 담당자 판정과 자동 판정의 일치율
5. 견적 1건당 검토 시간 감소율
6. 고가 후보 중 실제 협상으로 이어진 비율
7. 최종 발주가 기준 실현 절감액

## 8. 공통 예상 꼬리질문

### 데이터와 신뢰성

**Q. 기존 표준단가 엑셀을 그대로 쓰면 더 빠르지 않았습니까?**  
“그 파일은 초기 수작업 집계본이고 공급사·제조사·최근일이 일괄 입력되거나 문자열 기준으로 선택된 문제가 확인됐습니다. 현재 시스템은 같은 원본 견적에서 다시 계산하고, 과거 엑셀은 운영 정답으로 사용하지 않습니다.”

**Q. 신규 견적을 올리면 표준 DB가 자동 학습합니까?**  
“아닙니다. 신규 견적은 `신규 입찰` 역할로 분리됩니다. 실제 구매 결과와 검토 승인이 확인된 뒤 별도 절차로 과거 근거에 편입해야 기준 오염을 막을 수 있습니다.”

**Q. 중복 파일은 어떻게 처리합니까?**  
“파일과 품목 계보를 남기되 가격 통계에는 대표 한 건만 기여합니다. 최신 견적일, 개정번호, 정상 파싱 원본, 최근 수집본 순으로 대표를 선택합니다.”

**Q. 근거가 한 건뿐이어도 왜 사용합니까?**  
“원본과 정제가 확인된 한 건은 참고할 가치가 있습니다. 다만 `근거 1건·신뢰도 낮음`으로 표시해 다건 근거와 구분합니다.”

### AI와 자동화

**Q. 이게 AI 시스템입니까, 규칙 기반 시스템입니까?**  
“가격 계산과 판정은 감사 가능한 규칙·통계 방식입니다. AI는 사내에서 표현이 다른 유사 품목 후보를 찾는 보조 역할입니다. 가격을 생성형 AI가 만들어내지 않게 한 것이 이 업무에서는 안전장치입니다.”

**Q. AI가 잘못 매칭하면 어떻게 합니까?**  
“모호한 매칭은 자동 가격 판정에 사용하지 않고 판정 대기로 보냅니다. 모든 자동 결과에는 원본 근거가 연결돼 담당자가 확인할 수 있습니다.”

### 시장가

**Q. 왜 시장가가 대부분 조회되지 않습니까?**  
“견적의 상당 부분이 주문제작품·가공품·설치비이기 때문입니다. 공개 유통 사이트의 정확한 모델번호 상품에만 시장가가 존재합니다. 검색 결과가 없다는 것도 정상적인 결과입니다.”

**Q. 시장가를 못 찾으면 AI로 추정하면 안 됩니까?**  
“구매 가격은 작은 오차도 협상과 예산에 영향을 줍니다. 근거 없는 추정은 숫자가 있는 것처럼 보이게 만들기 때문에 사용하지 않습니다.”

**Q. 외부 사이트 가격과 실제 구매가는 다르지 않습니까?**  
“맞습니다. 그래서 시장가는 내부 표준 DB와 섞지 않고 보조 근거로만 저장합니다. MOQ, 재고, 세금, 배송 조건이 확인된 결과만 자동 비교에 사용합니다.”

### 운영과 보안

**Q. 지금 바로 전사 운영할 수 있습니까?**  
“현재는 로컬 파일럿이 가능한 수준입니다. 전사 운영에는 사내 서버, 사용자 인증과 권한, 백업·감사 정책, 보안해제본 재수집, 남은 양식 파서와 OCR 검증이 추가로 필요합니다.”

**Q. 왜 LOCAL MODE입니까?**  
“회사 견적 원본을 외부 서버로 보내지 않고 로컬에서 기능과 데이터 품질을 먼저 검증하기 위한 단계입니다. 운영 전환 시 사내 인프라와 인증체계에 맞춰 배치합니다.”

**Q. 외부 조회 시 회사 정보가 나갑니까?**  
“시장가 조회에는 품목명·모델 검색어가 외부 사이트로 전달될 수 있습니다. 사내 보안정책 검토가 필요하며, 민감한 프로젝트명이나 전체 견적 원본을 외부로 전송하는 구조는 아닙니다.”

**Q. 장애나 잘못된 업데이트는 어떻게 복구합니까?**  
“원본과 가격·분석 이력은 추가 방식으로 보존하고, DB 변경 전 백업을 만듭니다. 입력·규칙·코드가 맞지 않는 빌드는 신규 판정에 사용하지 않습니다.”

### 사업 효과

**Q. 실제로 얼마를 절감합니까?**  
“현재 화면은 절감 가능성을 보여줍니다. 확정 절감액을 주장하려면 실제 최종 발주가와 기존 방식의 기준가격을 비교하는 파일럿 측정이 필요합니다.”

**Q. 가장 큰 기대효과는 무엇입니까?**  
“첫째 검토 시간 단축, 둘째 고가 품목 누락 방지, 셋째 담당자 개인의 경험을 원본 근거가 있는 조직 자산으로 전환하는 것입니다.”

**Q. 다음 투자 우선순위는 무엇입니까?**  
“첫째 실제 발주·지급 가격 연계, 둘째 남은 223개 원본의 파서·OCR·보안해제, 셋째 품목 마스터와 제조사 모델 정비, 넷째 사내 서버·권한 구축, 다섯째 품목군별 물가지수와 계약조건 반영입니다.”

“현재 단계에서도 신규 견적의 고가·저가 후보를 빠르게 찾고, 각 판단을 원본까지 추적하며, 과거 최저가를 현재 가치로 환산한 협상 목표를 제시할 수 있습니다.”

“동시에 아직 읽지 못한 파일, 확신할 수 없는 품목, 조회되지 않는 시장가는 숨기지 않고 판정 대기로 남깁니다. 완벽한 숫자를 가장하는 대신, 믿을 수 있는 범위와 부족한 범위를 구분하는 것이 이 시스템의 운영 원칙입니다.”

“다음 단계는 실제 발주 결과와 연결해 효과를 측정하는 파일럿입니다. 견적 검토 시간, 자동 판정 커버리지, 협상 전환율과 실제 절감액을 측정하면 전사 운영 투자 여부를 객관적으로 판단할 수 있습니다.”

## 11. 발표 직전 점검표

### 11.1 전날

- 로컬 DB 백업을 만든다.
- 정제·표준 DB 재구축 작업을 발표 당일에는 실행하지 않는다.
- 구매 목표가 설명에 `실제로 구매했던 가격`이라는 문구가 남아 있다면
  `과거에 실제로 제출받은 견적 단가`로 수정한다. 현재 데이터의 원천은 지급·발주
  실적이 아니라 과거 제출 견적이므로 이 표현을 혼용하면 안 된다.
- 시연용 32품목 견적서가 열리는지 확인한다.
- KOSIS CPI 캐시에 2025년까지의 확정값이 있는지 확인한다.
- DeviceMart 조회 가능 여부와 Mouser API 키 상태를 확인한다.
- 시장가 실시간 조회가 불안하면 저장된 캐시 결과와 발표자료 화면을 예비 수단으로 준비한다.

### 11.2 발표 30분 전

- 백엔드와 프런트엔드를 실행한다.
- `정제 검토`, `표준 DB`, `신규 견적 분석`을 한 번씩 연다.
- 표준 DB의 `최근 갱신`과 목록을 확인한다.
- 시연 견적을 한 번 분석해 32개 품목이 파싱되는지 확인한다.
- 기본 임계값이 10%와 20%인지 확인한다.
- 목표가 산정 22건 여부와 CPI 기준연도를 확인한다.
- 외부 조회를 다시 실행할 필요가 없도록 유효한 캐시를 확인한다.
- 화면 배율은 100%, 라이트 모드로 맞춘다.

### 11.3 시연 중 장애 대응 문구

**외부 시장가가 안 나올 때**  
“외부 사이트나 사내망 상태가 불안정할 때 가격을 임의로 만들지 않는 것이 설계 원칙입니다. 현재는 판정 대기로 유지되고, 정상 조회 시 출처와 함께 캐시에 저장됩니다.”

**표준 DB 로딩이 늦을 때**  
“표준 DB는 원본 계보와 현재 빌드 지문까지 확인한 뒤 결과를 제공합니다. 발표 환경에서는 미리 로딩해 두며, 운영 전환 시 서버형 DB와 조회 최적화를 적용할 예정입니다.”

**목표가가 일부 비어 있을 때**  
“원본 날짜나 연간 CPI가 확인되지 않은 가격은 현재가치로 환산하지 않습니다. 빈칸은 계산 실패를 숨긴 것이 아니라 근거 부족을 표시한 것입니다.”

**시장가가 유사 상품만 나올 때**  
“유사 상품은 참고 링크일 뿐 자동 가격 판정에는 사용하지 않습니다. 정확한 모델과 거래조건이 맞아야만 근거로 채택합니다.”

## 12. 1분 요약본

“Price Analyzer는 회사가 받은 과거 견적을 품목별 표준 DB로 만들고, 신규 견적을 올리면 고가·저가·주의·적정 항목을 자동으로 선별하는 구매 지원 도구입니다. 내부 근거가 없을 때만 DeviceMart와 Mouser 시장가를 확인하며, 찾지 못하면 값을 추측하지 않고 판정 대기로 남깁니다. 구매 목표가는 원본 날짜가 확인된 과거 최저가를 KOSIS 소비자물가로 현재 가치에 맞춰 환산해 협상 출발점으로 제시합니다. 모든 가격은 원본 파일까지 추적할 수 있고, 현재 남아 있는 파서·OCR·보안 파일 문제도 수치로 공개합니다. 따라서 이 시스템의 가치는 100% 자동 정답이 아니라, 반복 검토 시간을 줄이고 협상 근거를 조직 자산으로 축적하는 데 있습니다.”
